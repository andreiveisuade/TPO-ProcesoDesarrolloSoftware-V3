# M7 — Adapter: `JwtUtil` detrás de `TokenService` + `UsuarioDetails`

## Patrón

**Adapter** (estructural): convertir la interfaz de una clase existente en la interfaz que espera el cliente. En V3 hay dos instancias:

| Rol | Adapter 1: token (nuevo en V3) | Adapter 2: usuario (existe desde V1, se documenta) |
|---|---|---|
| **Target** | `service/TokenService` (interfaz propia: `generarToken`, `extraerUsername`, `esValido`) | `UserDetails` de Spring Security |
| **Adapter** | `security/JwtUtil implements TokenService` | `security/UsuarioDetails implements UserDetails` |
| **Adaptee** | librería jjwt (`Jwts.builder()`, `Jwts.parser()`, `Claims`, `Keys`) | `IUsuario` / `Usuario` del dominio |
| **Client** | `AuthServiceImpl` (login/registro) y `JwtAuthFilter` (cada request) | `DaoAuthenticationProvider` (vía `UserDetailsServiceImpl`) |

## Problema (antes, `git show v2`)

`AuthServiceImpl` y `JwtAuthFilter` dependían de la clase concreta `JwtUtil`, que expone la API de jjwt sin interfaz propia:

```java
// AuthServiceImpl (v2)
private final JwtUtil jwtUtil;
...
return AuthResponse.desde(jwtUtil.generarToken(usuario.getUsername()), usuario);

// JwtAuthFilter (v2)
private final JwtUtil jwtUtil;
...
userDetails = userDetailsService.loadUserByUsername(jwtUtil.extraerUsername(token));
if (!jwtUtil.esValido(token, userDetails)) {
```

## Solución (después)

```java
// service/TokenService.java (Target)
public interface TokenService {
    String generarToken(String username);
    String extraerUsername(String token);
    boolean esValido(String token, UserDetails userDetails);
}

// security/JwtUtil.java (Adapter → Adaptee jjwt)
@Component
public class JwtUtil implements TokenService {
    @Override
    public String generarToken(String username) {
        return Jwts.builder().subject(username) ... .signWith(getKey()).compact();
    }
    ...
}

// AuthServiceImpl y JwtAuthFilter (Client)
private final TokenService tokenService;
...
return AuthResponse.desde(tokenService.generarToken(usuario.getUsername()), usuario);
```

`UsuarioDetails` no cambia de código: ya era un Adapter desde V1 (en V0 `Usuario implements UserDetails` con cuatro `return true`). Envuelve un `IUsuario` y traduce `getRol()` a `getAuthorities()`.

## Por qué

Los clientes de autenticación quedaban atados a una librería externa concreta (jjwt): cambiar de proveedor de tokens o mockearlo en un test obligaba a tocar el servicio y el filtro. Con `TokenService` como Target, la dependencia apunta a una abstracción propia (DIP) y la librería queda encerrada en un solo Adapter, igual que el dominio ya quedaba aislado de Spring Security con `UsuarioDetails`.

## Consecuencias

- Gana: los clientes no conocen jjwt; cambiar la implementación de tokens (otra librería, tokens opacos) o sustituirla en tests es tocar una sola clase.
- Cuesta: una interfaz más con una única implementación hoy; `esValido` sigue recibiendo `UserDetails`, así que el Target no está libre de Spring Security.
