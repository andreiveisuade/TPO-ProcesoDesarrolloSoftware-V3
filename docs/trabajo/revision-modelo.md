# Revisión del DER, el modelo y las capas V3 (T34, 06/10/2026)

Base: `main@6cfd4c2`. Solo lectura sobre el código. Las pruebas corrieron en instancias propias: la 8099 con el código de `main` y la 8098 con copias descartables sacadas con `git archive`, fuera del repo. La instancia del 8080 no se tocó.

Rutas de backend relativas a `backend/src/main/java/com/uade/tpejemplo/`.

## Veredicto

El modelo está bien plantado y se defiende: el estado del crédito es derivado (solo se guarda `anulado`), el agregado `Credito` → `Cuota` → `Cobranza` controla quién crea a quién y las reglas viven en las entidades. Las capas van en una sola dirección, sin `controller → repository`. No hay bloqueantes. Hay tres importantes: el esquema no impide dos cobranzas vigentes sobre la misma cuota (reproducido con requests concurrentes), los DTOs no acotan lo que las columnas aceptan (500 y redondeo silencioso) y el diagrama de clases detallado muestra dos métodos que ya no existen.

## 1. DER

Diagrama: `docs/diagramas/der-v3.puml` (renderizado a `der-v3.svg` y `der-v3.png`).

Cómo se obtuvo: DDL del log de Hibernate (`ddl-auto=create` sobre una base `mem` vacía, que es lo mismo que hace `update` al arrancar) y `INFORMATION_SCHEMA.INDEXES` / `TABLE_CONSTRAINTS` / `COLUMNS`, cargando ese DDL en un H2 2.3.232 descartable.

```sql
create table clientes (dni varchar(15) not null, nombre varchar(255) not null, primary key (dni))
create table creditos (anulado boolean not null, cantidad_cuotas integer not null check (cantidad_cuotas>=1), deuda_original numeric(12,2) not null, fecha date not null, importe_cuota numeric(12,2) not null, tasa_interes numeric(5,2) not null, id bigint generated by default as identity, dni_cliente varchar(15) not null, tipo_plan varchar(20) default 'INTERES_SIMPLE' not null, primary key (id))
create table cuotas (fecha_vencimiento date not null, importe numeric(12,2) not null, numero integer not null check (numero>=1), id bigint generated by default as identity, id_credito bigint not null, primary key (id), unique (id_credito, numero))
create table cobranzas (anulada boolean not null, fecha_cobranza date not null, importe numeric(12,2) not null, id bigint generated by default as identity, id_cuota bigint not null, primary key (id))
create table usuarios (puede_anular_cobranza boolean not null, puede_anular_credito boolean not null, id bigint generated by default as identity, password varchar(255) not null, username varchar(255) not null unique, rol enum ('ADMIN','SUPERVISOR','USER') not null, primary key (id))
-- FK: creditos.dni_cliente → clientes, cuotas.id_credito → creditos, cobranzas.id_cuota → cuotas (sin ON DELETE)
-- Índices: uno por PK, uno por FK, único (id_credito, numero) en cuotas, único username en usuarios
```

Los `check (>= 1)` salen de los `@Min(1)` de las entidades (Hibernate Validator los vuelca al DDL); el `enum` de `rol`, del `@Enumerated(EnumType.STRING)` con el dialecto de H2. `tipo_plan` queda como `varchar` sin check porque su `columnDefinition` pisa ese comportamiento (M-2).

### ¿El esquema protege las reglas del dominio?

| Regla | ¿La protege el esquema? | Dónde vive |
|---|---|---|
| DNI de cliente único | Sí: es la PK | también `service/impl/ClienteServiceImpl.java:26` (para dar 400 en vez de error de base) |
| Username único | Sí: `unique` | también `service/impl/AuthServiceImpl.java:34` |
| Número de cuota único por crédito y ≥ 1 | Sí: `unique (id_credito, numero)` y `check` | `model/Credito.java:99` `generarPlanDeCuotas` |
| Al menos una cuota, cuotas 1..N | Parcial: `cantidad_cuotas >= 1`, pero un crédito sin filas en `cuotas` es válido | `service/impl/CreditoServiceImpl.java:43` llama a `generarPlanDeCuotas` (backlog O6) |
| Rol válido | Sí: `enum` | `model/Rol.java` |
| Plan válido | No: `varchar(20)` libre | `model/TipoPlan.java` (M-2) |
| A lo sumo una cobranza vigente por cuota | **No** | `model/Cuota.java:79` `registrarCobranza`; se rompe con concurrencia (I-1) |
| No cobrar sobre un crédito anulado | No | `model/Cuota.java:74` |
| No anular un crédito con cobranzas vigentes | No | `model/Credito.java:145` `anular` |
| Importes > 0, tasa ≥ 0 | No (los `@Positive` están en los DTOs, no en las entidades) | `dto/request/CreditoRequest.java`, `dto/request/CobranzaRequest.java` |
| Largo y escala de cada campo | Sí, pero la API no lo sabe: responde 500 o redondea (I-2) | `@Column(length, precision, scale)` de las entidades |

Resumen: el esquema protege identidad, referencias, obligatoriedad y unicidad; las reglas de negocio con estado (pagada, anulado, vigente) dependen del código. Para un TP eso es correcto, salvo el caso de I-1, donde la regla del código no alcanza.

### Columnas derivadas o redundantes

- `creditos.anulado` contra el estado: **no hay redundancia**. No existe columna de estado; `model/Credito.java:111` `estado()` deriva VIGENTE / CANCELADO / ANULADO de `anulado` y de las cobranzas vigentes. `anulado` es el único hecho que no se puede derivar. `saldo` tampoco se guarda (`:118`).
- `creditos.importe_cuota`: derivado de deuda, tasa, cuotas y plan, y guardado a propósito como foto del otorgamiento (comentario en `model/Credito.java:48-50`). Si mañana cambia la fórmula, los créditos viejos no cambian de importe. Se defiende.
- `cuotas.importe`: repite `creditos.importe_cuota` en cada cuota. Es lo que permite el ajuste de la última cuota (backlog O3b) sin tocar el esquema. Se defiende.
- `cobranzas.importe`: hoy siempre igual a `cuotas.importe` (se exige el importe exacto, `model/Cuota.java:84`). Es el registro de lo que se cobró y deja la puerta abierta a pagos parciales (O8, descartado). Se defiende.
- `CreditoResponse` expone `anulado` y `estado` a la vez (`dto/response/CreditoResponse.java`): redundancia en la API, no en la base. El front todavía usa `anulado`; no vale la pena tocarlo.

## 2. Modelo del sistema

**Agregado.** `Credito` crea sus cuotas (`model/Credito.java:99`, constructor de `Cuota` package-private en `model/Cuota.java:52`) y `Cuota` crea su cobranza (`model/Cuota.java:73`, `Cobranza.registrar` package-private en `model/Cobranza.java:51`). Ningún servicio puede armar una cuota o una cobranza suelta. Es un agregado conceptual, no DDD estricto: cuotas y cobranzas tienen repositorio propio y `CobranzaServiceImpl` entra directo por `CuotaRepository`, sin pasar por el crédito. Para este alcance está bien; la cuota llega al crédito navegando `credito.isAnulado()`.

**Invariantes y estados.** Las reglas que importan para un dashboard de préstamos están en el modelo y con test: no cobrar dos veces ni con otro importe ni sobre un anulado (`model/Cuota.java:73`), no anular con cobranzas vigentes ni dos veces (`model/Credito.java:141`), anular cobranzas solo en el día y una vez (`model/Cobranza.java:59`), guardas de ADMIN en `model/Usuario.java:47,56`. El ciclo de vida VIGENTE → CANCELADO (al pagar la última) → VIGENTE (si se anula una cobranza) y VIGENTE → ANULADO sale solo, porque el estado es derivado. La mora (`model/Cuota.java:66` `estaVencida`) también.

**Inconsistencias entre diagrama de clases, DER y casos de uso:**

- `docs/diagramas/clases-v3.puml:218-221` y `:285-286` muestran `IPermisos.permiteAnularCredito()` / `permiteAnularCobranza()` y los mismos métodos en `Permisos`. Se borraron en `c718027`; el código tiene `isPuedeAnularCredito()` / `isPuedeAnularCobranza()` (`model/interfaces/IPermisos.java:5-7`). Lo arrastran `clases-v3-modelo.svg` y `.png` (I-3).
- La vista general (`clases-v3.puml:20-34`, `:56-70`) no tiene `AuthController.me`, `CreditoController.listarTodos` ni `AuthService.actual` / `CreditoService.listarTodos`, que existen y están documentados en los casos de uso (I-3).
- `Credito "1" *-- "1..*" Cuota` en el diagrama; el esquema admite 0 cuotas y la composición no tiene `cascade` en JPA (`model/Credito.java:68`): el servicio persiste las cuotas a mano (`service/impl/CreditoServiceImpl.java:43`). La composición UML habla de ciclo de vida, y como nunca se borra nada se cumple; el hueco del crédito sin plan ya está en el backlog (O6).
- `Cuota "1" *-- "0..*" Cobranza` es correcto, pero ni el diagrama ni el esquema dicen "a lo sumo una vigente" (I-1). El DER nuevo lo anota.
- Casos de uso: coinciden con el código en todo lo revisado (códigos HTTP, reglas, dónde vive cada una). Lo único que falta en sus huecos es I-2: UC04 dice que el DNI no tiene formato, pero no que un DNI de más de 15 caracteres da 500.
- `EstadoCredito` está en el diagrama de clases y no en el DER: es intencional (derivado) y el DER lo aclara en una nota.

## 3. Capas de Spring Boot

Dependencias entre paquetes, sacadas con `grep -rn "^import com.uade"`:

| Desde | Hacia | Comentario |
|---|---|---|
| `controller` | `service`, `dto`, `security` (`UsuarioDetails` por `@AuthenticationPrincipal`) | Ningún `controller → repository` ni `controller → model` |
| `service` | `repository`, `model`, `dto`, `exception` | No importa `security` del proyecto; sí excepciones y beans de Spring Security (`AccessDeniedException`, `PasswordEncoder`, `AuthenticationManager`) |
| `security` | `service` (`TokenService`), `repository`, `model` | `JwtUtil` implementa el puerto `TokenService` que define `service`: la dependencia apunta hacia adentro (Adapter, M7) |
| `model` | `exception` (`BusinessException`) | Fuera de eso, solo anotaciones de JPA y Bean Validation |
| `dto` | `model` | Las respuestas se arman desde las interfaces (`ICredito`, `ICuota`, `ICobranza`), no desde las clases concretas |
| `repository` | `model` | |
| `exception` | `dto` (`ErrorResponse`) | Cierra un ciclo de paquetes `model → exception → dto → model` (M-4) |
| `config` | `security`, `repository`, `model` | Seguridad, OpenAPI y la semilla |

Cada clase está en su capa. Lo que queda en el borde:

- **Lógica de negocio fuera del modelo**: la autorización de anulación está en los servicios (`service/impl/CreditoServiceImpl.java:80`, `service/impl/CobranzaServiceImpl.java:51`) navegando `usuario.getPermisos()`; ya está en el backlog como BS3. El filtro "sin ADMIN" de `service/impl/AdminServiceImpl.java:30` es regla del caso de uso, bien ubicada. La regla "lo anulado no cuenta" está duplicada en JPQL (`repository/CreditoRepository.java:33`, `repository/CobranzaRepository.java:18`) y en el modelo (M-6).
- **Lógica de persistencia en el servicio**: la precarga de cobranzas por efecto lateral (`service/impl/CreditoServiceImpl.java:58,71,99`, sin usar el resultado) y la persistencia manual de los hijos del agregado (`:43`, `service/impl/CobranzaServiceImpl.java:36`). La primera tiene un comentario que no es cierto (M-1); la segunda es O6.
- `spring.jpa.open-in-view=false` y el mapeo a DTO adentro del `@Transactional` de cada servicio: ninguna carga lazy se escapa al controller.

## 4. Lo que está bien (para defenderlo)

- **Estado derivado**: una sola columna (`anulado`) y el resto calculado por el experto (`Credito.estado()`, `saldo()`, `Cuota.estaPagada()`, `estaVencida()`). No hay estado guardado que se pueda desincronizar.
- **Creación controlada**: factories `nuevo` y constructores package-private; el id, el importe de cuota, las cuotas y la fecha de la cobranza no se reciben desde afuera (Creator).
- **Reglas en las entidades** (Information Expert) y con test: 25 de los 26 tests son de `model/`.
- **Esquema sólido en lo estructural**: todo NOT NULL, FK completas, unicidad de DNI, username y número de cuota por crédito, checks de `@Min`, `rol` como enum.
- **Baja lógica**: anular no borra; las FK sin `ON DELETE` son coherentes con eso y el historial queda entero.
- **Capas en una dirección**, DTOs que dependen de interfaces del modelo, `TokenService` como puerto implementado por `security` (Adapter + inversión de dependencias).

## 5. Hallazgos

### BLOQUEANTE

Ninguno.

### IMPORTANTE

**I-1. Dos cobranzas vigentes sobre la misma cuota con requests concurrentes.**
- Evidencia: `service/impl/CobranzaServiceImpl.java:31-36` lee la cuota con sus cobranzas (`repository/CuotaRepository.java:30-34`), `model/Cuota.java:79` decide que está impaga y recién después inserta; nada serializa dos requests y el esquema no tiene restricción (no puede tener un `unique` porque las anuladas también cuentan). Reproducido en la 8099: crédito de 1 cuota, 20 `POST /api/cobranzas` en paralelo → 7, 3 y 2 cobranzas vigentes en tres corridas; el dashboard quedó con cobrado 12.000,00 contra financiado 3.100,56.
- Arreglo mínimo (probado en una copia, 8098): en `CuotaRepository.buscarPorCreditoYNumero` agregar `@Lock(LockModeType.PESSIMISTIC_WRITE)` **y sacar el `LEFT JOIN FETCH c.cobranzas`**. Con el join puesto, Hibernate emite `for update` pero sigue duplicando (10, 2 y 1 vigentes): H2 lee las cobranzas del join con la foto de antes del bloqueo. Sin el join, las cobranzas se cargan lazy después de obtener el lock y ven la que se acaba de commitear: 1 sola vigente en 5 corridas de 20, y el flujo cobrar → anular → recobrar → rechazar sigue igual.
- Cuándo: backlog 27/10, con un `@DataJpaTest` (T-2). No antes del 13/10: la demo no lo expone (el botón Registrar se deshabilita mientras la request está en curso, `frontend/src/pages/Cobranzas.jsx:77`) y el arreglo cambia la query de un flujo que se ejecuta en vivo. Si se decide hacerlo antes, está probado.

**I-2. Los DTOs no acotan largo ni escala: 500 o dato cambiado sin aviso.**
- Evidencia (8099): `POST /api/clientes` con DNI de 16 caracteres → 500 (`Value too long for column`, la columna es `varchar(15)`); nombre de 300 caracteres → 500; crédito con deuda 99.999.999.999 → 500; deuda 9.000.000.000 al 45 % en 1 cuota → 500 (el desborde está en `importe_cuota`). Crédito con deuda 100.555 y tasa 10.125: el `POST` responde 201 con 100.555 y 10.125, el `GET` siguiente devuelve 100.56 y 10.13. Campos: `dto/request/ClienteRequest.java:10,13`, `dto/request/CreditoRequest.java:23,32`, `dto/request/CobranzaRequest.java:20`, `dto/request/RegisterRequest.java:11`.
- Arreglo mínimo, solo anotaciones en los DTOs: `@Size(max = 15)` en `dni` y `dniCliente`, `@Size(max = 255)` en `nombre` y `username`, `@Digits(integer = 8, fraction = 2)` en `deudaOriginal` (con tasa hasta 999,99 % y 1 cuota, el importe entra en `numeric(12,2)`), `@Digits(integer = 3, fraction = 2)` en `tasaInteres`, `@Digits(integer = 10, fraction = 2)` en `importe`. Todo pasa a 400 por `handleValidation`, que ya existe.
- Cuándo: antes del 13/10. No toca el modelo y se verifica con las mismas requests.

**I-3. El diagrama de clases detallado muestra métodos que no existen.**
- Evidencia: `docs/diagramas/clases-v3.puml:218-221,285-286` (`permiteAnularCredito()` / `permiteAnularCobranza()`, borrados en `c718027`); el código usa `isPuedeAnularCredito()` / `isPuedeAnularCobranza()` (`model/interfaces/IPermisos.java:5-7`). La vista general omite `AuthController.me`, `CreditoController.listarTodos`, `AuthService.actual` y `CreditoService.listarTodos`. `docs/diagramas/` va en el zip (solo `docs/trabajo` es `export-ignore`) y la vista general está embebida en `docs/reporte/reporte-v3.html`.
- Arreglo mínimo: corregir esas líneas del `.puml`, re-renderizar `clases-v3-general` y `clases-v3-modelo` (svg y png) y regenerar el reporte.
- Cuándo: antes del 13/10. Es solo documentación.

### MENOR

**M-1. La precarga de cobranzas no evita un error, evita N+1, y el arreglo que propone el backlog falla en runtime.**
- Evidencia: el comentario de `service/impl/CreditoServiceImpl.java:98` dice que `Cuota.estaPagada()` necesita la precarga, y la fila I2 del backlog dice que sin ella "tira `LazyInitializationException`". Probado en una copia sin las tres líneas (`:58`, `:71`, `:99`): `GET /api/creditos/{id}`, `GET /api/creditos`, el dashboard y la anulación responden bien y no hay `LazyInitialization` en el log, porque el mapeo corre dentro del `@Transactional`. Lo que cambia es la cantidad de consultas: 6 `select` para un crédito de 4 cuotas. Además, el `@EntityGraph` que propone I2 sobre `cuotas` y `cuotas.cobranzas` choca con que las dos son `List` (bags) y Hibernate rechaza traer dos bags juntas (`MultipleBagFetchException`, comportamiento documentado; no lo corrí).
- Arreglo mínimo: para la defensa, la respuesta correcta es "evita N+1". En el backlog, reescribir I2 como `spring.jpa.properties.hibernate.default_batch_fetch_size` en `application.properties` y borrar las tres líneas.
- Cuándo: corregir el texto de I2 ya; el cambio de código al 27/10.

**M-2. `tipo_plan` sin restricción y con un default que no corresponde.**
- Evidencia: `model/Credito.java:61` `columnDefinition = "varchar(20) default 'INTERES_SIMPLE'"`. Genera un `varchar` libre (a `rol` Hibernate le genera `enum`) y un default para "créditos ya existentes" (`docs/trabajo/m9.md:58`) que con H2 en memoria no existen nunca; el dominio dice que el plan es obligatorio.
- Arreglo mínimo: sacar el `columnDefinition`.
- Cuándo: backlog 03/11, junto con S9 (`ddl-auto`).

**M-3. Carrera entre anular un crédito y cobrar una de sus cuotas.** No reproducida. `CreditoServiceImpl.anularCredito` y `CobranzaServiceImpl.registrar` tocan filas distintas (`creditos` contra `cobranzas`) sin bloqueo, así que dos usuarios a la vez podrían dejar un crédito ANULADO con una cobranza vigente. Mismo arreglo que I-1, bloqueando también el crédito. Backlog 27/10, con I-1.

**M-4. Ciclo de paquetes `model → exception → dto → model`.** El paquete `exception` mezcla excepciones de dominio (`BusinessException`, que usa el modelo) con el `@RestControllerAdvice` (`exception/GlobalExceptionHandler.java:3` importa `dto.response.ErrorResponse`). Entre clases no hay ciclo. Arreglo: mover `GlobalExceptionHandler` a `controller`. Backlog 03/11; tal como está se defiende.

**M-5. Composición sin `cascade`.** Los servicios guardan los hijos del agregado por su propio repositorio (`service/impl/CreditoServiceImpl.java:43`, `service/impl/CobranzaServiceImpl.java:36`). Ya cubierto por O6. Para la defensa: la composición del diagrama es de ciclo de vida, y nada se borra.

**M-6. La regla "lo anulado no cuenta" está en dos lugares.** En JPQL (`repository/CreditoRepository.java:33`, `repository/CobranzaRepository.java:18`) y en el modelo (`Credito.estado()`, `Cuota.estaPagada()`); el dashboard mezcla un conteo en memoria que carga toda la cartera (`service/impl/DashboardServiceImpl.java:40-42`) con sumas en SQL. Ya documentado en UC16 (H3/P2). Se defiende como agregación en la base; sin acción.

**M-7. `save()` sobre entidades ya gestionadas.** `service/impl/CreditoServiceImpl.java:87`, `service/impl/CobranzaServiceImpl.java:59`, `service/impl/AdminServiceImpl.java:45,56`: el dirty checking ya persiste el cambio. Inocuo, explicita la intención. Sin acción.

**M-8. `cantidadCuotas` sin máximo.** `dto/request/CreditoRequest.java:36` solo tiene `@Min(1)`; un crédito a 100.000 cuotas genera 100.000 filas en una request. No lo probé. Si se hace I-2, sumar un `@Max`.

## 6. Cómo reproducir I-1 e I-2

Sobre una instancia propia (`mvn -q spring-boot:run -Dspring-boot.run.arguments="--server.port=8099"` en `backend/`), con `H="Authorization: Bearer <token de admin>"` y un cliente `99`:

```bash
B=http://localhost:8099/api; J='Content-Type: application/json'
ID=$(curl -s -XPOST $B/creditos -H "$H" -H "$J" -d '{"dniCliente":"99","deudaOriginal":1000,"fecha":"2026-10-01","tasaInteres":0,"cantidadCuotas":1,"tipoPlan":"INTERES_SIMPLE"}' | sed -E 's/^\{"id":([0-9]+).*/\1/')
seq 20 | xargs -P 20 -I{} curl -s -o /dev/null -w '%{http_code}\n' -XPOST $B/cobranzas -H "$H" -H "$J" -d "{\"idCredito\":$ID,\"numeroCuota\":1,\"importe\":1000}" | sort | uniq -c
curl -s $B/cobranzas/credito/$ID -H "$H" | grep -o '"anulada":false' | wc -l   # más de 1 = I-1

curl -s -w ' [%{http_code}]\n' -XPOST $B/clientes -H "$H" -H "$J" -d '{"dni":"1234567890123456","nombre":"x"}'   # 500 = I-2
```
