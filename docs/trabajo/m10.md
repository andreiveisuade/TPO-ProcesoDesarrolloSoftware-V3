# M10 — Dashboard para ADMIN

## Patrón
Control de acceso por rol (autorización declarativa en `SecurityConfig`). Sin patrón de diseño nuevo: corrección de una regla de acceso.

## Problema (código antes)
`config/SecurityConfig.java`, `filterChain`:

```java
.requestMatchers("/api/supervisor/**", "/api/dashboard/**").hasRole("SUPERVISOR")
```

Front: `Dashboard.jsx` (`user?.rol === 'SUPERVISOR'`) y `Navbar.jsx` (`{isSupervisor && <Link to="/estadisticas">}`).

## Solución (código después)
```java
.requestMatchers("/api/supervisor/**").hasRole("SUPERVISOR")
.requestMatchers("/api/dashboard/**").hasAnyRole("SUPERVISOR", "ADMIN")
```

Front: `Dashboard.jsx` usa `puedeVerDashboard = rol === 'SUPERVISOR' || rol === 'ADMIN'` y `Navbar.jsx` muestra el link con `(isSupervisor || isAdmin)`.

## Por qué
H10 / TPO-010: el ADMIN no podía ver el dashboard por el `hasRole("SUPERVISOR")` exacto. Se separó el matcher de `/api/supervisor/**` para que los permisos de anulación sigan siendo solo del supervisor. Pendiente confirmar con Regulo que el ADMIN debe ver el dashboard.

## Consecuencias
Gana: el administrador accede a las estadísticas sin cambiarse de rol. Cuesta: la regla de visibilidad queda duplicada en backend y en dos componentes del front, y hay un matcher más en `SecurityConfig`.
